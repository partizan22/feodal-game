# Формат централізованого опису зв'язків моделей

Статус: погоджений базовий формат; конкретні зв'язки, кардинальності, SQL-імена та напрямки DFS заповнюються окремо.

Цей документ визначає формат майбутнього файлу `config/relationships.yaml`. Сам файл із повним переліком зв'язків поки не створюється.

Пов'язаний контракт: [BASE_MODEL.md](BASE_MODEL.md), розділи 5–8.

## 1. Принципи

- **Один логічний зв'язок — один запис.** Не дублюємо його опис у зворотному напрямку.
- Між тією самою парою типів моделей може бути **кілька різних зв'язків**. Кожен має унікальний ключ (наприклад, `army_current_region` та `movement_current_region`).
- Запис незалежно визначає: **(1)** моделі й кардинальність; **(2)** характеристики, через які зв'язок доступний; **(3)** спосіб отримання зв'язку (`storage`); **(4)** напрямки DFS.
- Спосіб отримання зв'язку та DFS-напрямки **не виводяться автоматично** з кардинальності чи назв характеристик.
- Джерело істини для прямого зв'язку — контрольований state моделі. SQL-проєкція потрібна для пошуку/зворотного lookup.
- Для поточного набору моделей немає потреби в одному зв'язку з **двома прямими характеристиками**. Типовий випадок — одна пряма характеристика і необов'язкова зворотна обчислювальна. Зв'язки без прямої характеристики допускаються, але потребують явного способу отримання значення.

## 2. Структура запису

```yaml
relationships:
  unique_relationship_key:
    models:
      A: ModelA
      B: ModelB
    type: ManyToOne
    characteristics:
      A: { name: related_model, type: direct }
      B: { name: related_models[], type: computed-relation }
    storage:
      type: fk
      # параметри відповідного типу storage
    dfs:
      A_depends_on_B: true
      B_depends_on_A: false
```

- `models.A`, `models.B` — умовні сторони **цього конкретного запису**, а не глобальна орієнтація моделей.
- `type` — кардинальність **від A до B**: `OneToOne`, `OneToMany`, `ManyToOne`, `ManyToMany`. Наприклад, `ManyToOne`: багато A можуть посилатися на один B.
- `characteristics.A/B` — назва характеристики та спосіб отримання: `direct` (зі state) або `computed-relation` (визначає інфраструктура). Якщо відповідної характеристики немає, вказуємо `null`. Назви, включно із суфіксом `[]`, зберігаємо буквально.
- `storage` — спосіб отримання зв'язку: `fk`, `list-junction` або `custom`, **незалежний від DFS**. Для `custom` SQL-проєкція не створюється.
- `dfs.A_depends_on_B: true` означає, що зміна зовнішньої сигнатури **B** може вимагати обходу **A**. `dfs.B_depends_on_A` — аналогічно у зворотному напрямку. Обидва прапорці обов'язкові; допустимі всі чотири комбінації.
- Для `computed-relation` стандартний спосіб отримання значення — зворотний SQL lookup. Для нестандартного зв'язку використовується `storage.type: custom`: інфраструктура викликає статичний метод зазначеного класу моделі, який повертає ID пов'язаних моделей.
- Для самозв'язків (`Region` → `Region`) A і B залишаються ролями в одному записі, навіть якщо клас однаковий. Роль визначається характеристикою; окремого механізму симетрії немає. За симетричність `neighbors[]` відповідає метод моделі.
- Кардинальність `type` — опис зв'язку, а не вимога додаткової автоматичної перевірки унікальності інфраструктурою.

## 3. Типи `storage`

Підтримуємо **лише три типи**:

### `fk`

Зовнішній ключ у SQL-таблиці моделі, що містить пряме одиничне посилання.

```yaml
storage:
  type: fk
  table: armies
  column: player_id
```

Колонка є проєкцією прямої характеристики, а не самостійним джерелом ігрового state. Setter позначає `fk` як dirty; колонка синхронізується під час `flush-before-query` або перед commit.

### `list-junction`

Проміжна SQL-таблиця для **прямої характеристики-списку посилань на моделі** (наприклад, `CombatSituation.defenders[]` або `Movement.route[]`).

```yaml
storage:
  type: list-junction
  table: combat_situation_defenders
  owner_column: combat_situation_id
  target_column: army_id
```

- Setter прямого списку змінює state та позначає проєкцію як dirty, **без негайного SQL-запису**.
- Під час `flush` проєкція повністю синхронізується: старі рядки конкретної моделі-власника видаляються, актуальні створюються заново.
- Кілька змін списку до `flush` об'єднуються; записується лише актуальний склад.
- **Перед SQL-запитом, що залежить від цих змін**, інфраструктура виконує `flush` потрібних dirty проєкцій у транзакції GameEvent; reverse lookup бачить актуальний список.
- Перед фінальним commit виконується `flush` усіх проєкцій, що залишилися dirty. Rollback скасовує вже виконані SQL-оновлення.
- Джерело істини — пряма характеристика моделі, а не проміжна таблиця.
- Для прямих списків порядок елементів завжди зберігається. Якщо SQL-проєкція повинна відтворювати цей порядок (наприклад, `Movement.route[]`), використовуємо `position_column`.
- Назви таблиць і колонок у прикладах **ілюстративні**, а не затверджений SQL DDL.

**Звичайний `junction` поки не реалізуємо.** Його не слід використовувати у деклараціях поточної версії.

### `custom`

Зв'язок визначається статичним методом зазначеної моделі, без SQL-проєкції:

```yaml
storage:
  type: custom
  model: Region
  method: resolve_neighbors
```

Інфраструктура викликає `Region::resolve_neighbors(EventContext $context, int $regionId): array`, передаючи контекст події та ID поточної області. Метод повертає масив ID сусідніх областей; для одиничного зв'язку — один ID або `null`. Отримані ID використовуються стандартними relationship getter / `LazyCollection`, без завантаження моделей під час читання `_id`. Порядок ID у колекції зберігається таким, як його повернув метод.

Для зворотних `computed-relation` через SQL порядок елементів **не гарантований** (якщо явно не задано сортування). Стандартні SQL lookup і `custom` методи виключають умовно видалені моделі. У `custom` методі відповідальність за це правило лежить на реалізації методу.

## 4. Приклади

### Пряме одиничне посилання зі зворотним lookup

```yaml
relationships:
  army_player:
    models: { A: Army, B: Player }
    type: ManyToOne
    characteristics:
      A: { name: player, type: direct }
      B: { name: "armies[]", type: computed-relation }
    storage:
      type: fk
      table: armies
      column: player_id
    dfs:
      A_depends_on_B: true
      B_depends_on_A: true
```

Значення DFS у цьому прикладі показують **формат**, а не затверджені напрямки конкретного зв'язку.

### Прямий список із проміжною таблицею

```yaml
relationships:
  combat_defenders:
    models: { A: CombatSituation, B: Army }
    type: ManyToMany
    characteristics:
      A: { name: "defenders[]", type: direct }
      B: null
    storage:
      type: list-junction
      table: combat_situation_defenders
      owner_column: combat_situation_id
      target_column: army_id
    dfs:
      A_depends_on_B: false
      B_depends_on_A: false
```

Значення DFS тут лише демонстраційні. Напрямок зберігання `CombatSituation.defenders[]` / `Army.active_defender_combat_situation` поки не остаточно затверджено.

### Зв'язок без прямої характеристики

```yaml
relationships:
  region_neighbors:
    models: { A: Region, B: Region }
    type: ManyToMany
    characteristics:
      A: { name: "neighbors[]", type: computed-relation }
      B: null
    storage:
      type: custom
      model: Region
      method: resolve_neighbors
    dfs:
      A_depends_on_B: false
      B_depends_on_A: false
```

## 5. Правила валідації

- Унікальний ключ кожного запису; обидві моделі мають існувати.
- Усі зазначені характеристики мають бути оголошені в належних моделях.
- Не дублювати один і той самий логічний зв'язок перестановкою A/B.
- `type`, `storage.type` та обидва DFS-прапорці обов'язкові.
- Для `fk` потрібні `table` і `column`; для `list-junction` — `table`, `owner_column`, `target_column`; для `custom` — `model` і `method` статичного методу.
- `list-junction` застосовується до **прямого списку**, а не до обчислювальної колекції.
- Відсутність зворотної характеристики допустима.
- Спосіб розв'язання `computed-relation` повинен бути однозначним: зворотний SQL lookup або `storage.type: custom` зі статичним методом моделі.
- Для `Region.neighbors[]` це `Region::resolve_neighbors(...)`, що визначає сусідів за координатами. SQL junction-таблиця не потрібна.
- Стандартні SQL lookup і `custom` не повертають умовно видалені моделі; додаткової перевірки кардинальності інфраструктурою не вводимо.
- Напрямки DFS перевіряються за реальними залежностями computed characteristics, а не за формою FK.

## 6. Межі специфікації

Цей документ фіксує **формат** декларації, але не затверджує повний перелік зв'язків, значення DFS чи SQL DDL. Для `storage.type: custom` погоджено виклик статичного методу моделі, що повертає ID пов'язаних моделей.

**Синхронізація з `BASE_MODEL.md`:** для `fk` і `list-junction` діє однакова стратегія **flush-before-query**. Setter лише змінює state і позначає проєкцію як dirty; перед залежним SQL lookup виконується flush, а перед commit — flush решти. Для `list-junction` flush повністю замінює рядки відповідного власника списку. SQL lookup не повинен бачити застарілу проєкцію.
