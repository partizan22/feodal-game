# Формат централізованого опису зв'язків моделей

Статус: погоджений базовий формат; конкретні зв'язки, кардинальності, SQL-імена та напрямки DFS заповнюються окремо.

Цей документ визначає формат майбутнього файлу `config/relationships.yaml`. Сам файл із повним переліком зв'язків поки не створюється.

Пов'язаний контракт: [BASE_MODEL.md](BASE_MODEL.md), розділи 5–8.

## 1. Принципи

- **Один логічний зв'язок — один запис.** Не дублюємо його опис у зворотному напрямку.
- Між тією самою парою типів моделей може бути **кілька різних зв'язків**. Кожен має унікальний ключ (наприклад, `army_current_region` та `movement_current_region`).
- Запис незалежно визначає: **(1)** моделі й кардинальність; **(2)** характеристики, через які зв'язок доступний; **(3)** SQL-проєкцію; **(4)** напрямки DFS.
- SQL-проєкція та DFS-напрямки **не виводяться автоматично** з кардинальності чи назв характеристик.
- Джерело істини для прямого зв'язку — контрольований state моделі. SQL-проєкція потрібна для пошуку/зворотного lookup.
- Для поточного набору моделей немає потреби в одному зв'язку з **двома прямими характеристиками**. Типовий випадок — одна пряма характеристика і необов'язкова зворотна обчислювальна. Зв'язки без прямої характеристики допускаються, але потребують явного способу отримання значення.

## 2. Структура запису

```yaml
relationships:
  unique_relationship_key:
    models:
      A: ModelA
      B: ModelB
    type: ManyToOne
    characteristics:
      A: { name: related_model, type: direct }
      B: { name: related_models[], type: system_computed }
    storage:
      type: fk
      # метадані відповідного типу SQL-проєкції
    dfs:
      A_depends_on_B: true
      B_depends_on_A: false
```

- `models.A`, `models.B` — умовні сторони **цього конкретного запису**, а не глобальна орієнтація моделей.
- `type` — кардинальність **від A до B**: `OneToOne`, `OneToMany`, `ManyToOne`, `ManyToMany`. Наприклад, `ManyToOne`: багато A можуть посилатися на один B.
- `characteristics.A/B` — назва характеристики та спосіб отримання: `direct` (зі state) або `system_computed` (визначає інфраструктура). Якщо відповідної характеристики немає, вказуємо `null`. Назви, включно із суфіксом `[]`, зберігаємо буквально.
- `storage` — SQL-проєкція, **незалежна від DFS**.
- `dfs.A_depends_on_B: true` означає, що зміна зовнішньої сигнатури **B** може вимагати обходу **A**. `dfs.B_depends_on_A` — аналогічно у зворотному напрямку. Обидва прапорці обов'язкові; допустимі всі чотири комбінації.
- Для нестандартних `system_computed` зв'язків можна додати `resolver`. Його детальний синтаксис визначимо окремо. Не можна вважати відфільтровану характеристику повним зворотним відображенням прямого списку без окремого правила.

## 3. Типи SQL-проєкцій

Підтримуємо **лише три типи**:

### `fk`

Зовнішній ключ у SQL-таблиці моделі, що містить пряме одиничне посилання.

```yaml
storage:
  type: fk
  table: armies
  column: player_id
```

Колонка є проєкцією прямої характеристики, а не самостійним джерелом ігрового state.

### `list-junction`

Проміжна SQL-таблиця для **прямої характеристики-списку посилань на моделі** (наприклад, `CombatSituation.defenders[]` або `Movement.route[]`).

```yaml
storage:
  type: list-junction
  table: combat_situation_defenders
  owner_column: combat_situation_id
  target_column: army_id
```

- При **кожному збереженні моделі-власника** список у проміжній таблиці **повністю синхронізується** з поточним прямим списком: старі рядки цього екземпляра видаляються, актуальні створюються заново.
- Джерело істини — пряма характеристика моделі, а не проміжна таблиця.
- Оновлення виконується в транзакції GameEvent.
- Якщо порядок елементів має значення (наприклад, `Movement.route[]`), проєкція має зберігати його. Для цього передбачаємо необов'язковий `position_column`.
- Назви таблиць і колонок у прикладах **ілюстративні**, а не затверджений SQL DDL.

**Звичайний `junction` поки не реалізуємо.** Його не слід використовувати у деклараціях поточної версії.

### `none`

SQL-проєкції немає. Застосовується, якщо зв'язок визначається іншим способом (наприклад, геометрією карти або спеціальним resolver).

```yaml
storage:
  type: none
```

## 4. Приклади

### Пряме одиничне посилання зі зворотним lookup

```yaml
relationships:
  army_player:
    models: { A: Army, B: Player }
    type: ManyToOne
    characteristics:
      A: { name: player, type: direct }
      B: { name: "armies[]", type: system_computed }
    storage:
      type: fk
      table: armies
      column: player_id
    dfs:
      A_depends_on_B: true
      B_depends_on_A: true
```

Значення DFS у цьому прикладі показують **формат**, а не затверджені напрямки конкретного зв'язку.

### Прямий список із проміжною таблицею

```yaml
relationships:
  combat_defenders:
    models: { A: CombatSituation, B: Army }
    type: ManyToMany
    characteristics:
      A: { name: "defenders[]", type: direct }
      B: null
    storage:
      type: list-junction
      table: combat_situation_defenders
      owner_column: combat_situation_id
      target_column: army_id
    dfs:
      A_depends_on_B: false
      B_depends_on_A: false
```

`Army.active_defender_combat_situation` повертає лише **активну** ситуацію, тому не є автоматично повним зворотним відображенням `defenders[]`; її resolver/прив'язку слід визначити окремо. Значення DFS тут також лише демонстраційні.

### Зв'язок без прямої характеристики

```yaml
relationships:
  region_neighbors:
    models: { A: Region, B: Region }
    type: ManyToMany
    characteristics:
      A: { name: "neighbors[]", type: system_computed }
      B: null
    storage:
      type: none
    resolver: custom  # конкретний контракт resolver ще не затверджено
    dfs:
      A_depends_on_B: false
      B_depends_on_A: false
```

## 5. Правила валідації

- Унікальний ключ кожного запису; обидві моделі мають існувати.
- Усі зазначені характеристики мають бути оголошені в належних моделях.
- Не дублювати один і той самий логічний зв'язок перестановкою A/B.
- `type`, `storage.type` та обидва DFS-прапорці обов'язкові.
- Для `fk` потрібні `table` і `column`; для `list-junction` — `table`, `owner_column`, `target_column`.
- `list-junction` застосовується до **прямого списку**, а не до обчислювальної колекції.
- Відсутність зворотної характеристики допустима.
- Спосіб розв'язання `system_computed` зв'язку повинен бути однозначним: зворотний SQL lookup або явний resolver.
- Напрямки DFS перевіряються за реальними залежностями computed characteristics, а не за формою FK.

## 6. Межі специфікації

Цей документ фіксує **формат** декларації, але не затверджує повний перелік зв'язків, значення DFS, SQL DDL чи синтаксис нестандартних resolver.

**Питання синхронізації з `BASE_MODEL.md`:** поточний контракт базового класу описує негайне оновлення FK/junction при setter, тоді як для `list-junction` тут зафіксовано повне оновлення **при кожному збереженні моделі**. Перед реалізацією потрібно узгодити точку синхронізації так, щоб reverse lookup усередині GameEvent не читав застарілу проєкцію.
